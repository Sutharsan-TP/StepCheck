# Deployment

The backend runs on **Render** (a Python web service). The frontend runs on **Vercel**. Both deploy from the GitHub repository. Each needs the other's URL, so deploy in this order: backend, frontend, then add the frontend's URL to the backend's CORS setting.

## 1. Backend on Render

1. Push `main` to GitHub.
2. In Render, choose **New → Blueprint** and select the repository. Render reads [`render.yaml`](../render.yaml), which sets up:

   | Setting | Value |
   |---|---|
   | Service | `stepcheck-api`, free plan, Python 3.12.6, root directory `backend` |
   | Build | `pip install -r requirements.txt` |
   | Start | `uvicorn app.main:app --host 0.0.0.0 --port $PORT`, as a single process |
   | Health check | `/api/v1/health` |
   | `PROGRESS_TOKEN_SECRET` | Generated by Render, so it survives restarts and redeploys |
   | `TRUST_PROXY=true`, `TRUSTED_PROXY_HOPS=2` | Rate limits use the real client address (see [Checking the rate limiter](#checking-the-rate-limiter)) |

3. Render asks for the values marked `sync: false`.
   - **`CORS_ORIGINS`:** leave it blank for now. You'll set it in step 3 below.
   - **OpenRouter settings:** leave them blank until you have a key. Typed checking and corrections work without one.
4. When the deploy finishes, open `https://<your-service>.onrender.com/api/v1/health`. It should return `{"status":"healthy",...}`.

**Calculus worker.** The first calculus request starts a worker process that loads SymPy (about 60 MB measured on Windows, likely more on Linux, and a few seconds). The server starts it when it boots, so the free tier's 512 MB is enough for the API and one worker. `CALC_WORKERS` (default 1) and `CALC_JOB_TIMEOUT_SECONDS` (default 4) tune it. After a deploy, check Render's memory graph once after a few calculus requests.

**Keep it to one process.** Verifications, rate limits and guided progress are stored in memory. Running several workers or instances would split them, and a request could reach a process that doesn't have the data.

## 2. Frontend on Vercel

1. In Vercel, choose **Add New → Project** and import the repository.
2. Set **Root Directory** to `frontend`. Vercel detects Next.js and its build settings automatically.
3. Add the environment variable `NEXT_PUBLIC_API_URL` = `https://<your-service>.onrender.com`, with no trailing slash.
   - This value is built into the JavaScript bundle. If you change it later, **redeploy** for the change to take effect.
4. Under **Settings → Build and Deployment → Node.js Version**, choose 24.x (or 22.x).
5. Deploy, then note the production URL, for example `https://stepcheck.vercel.app`.

## 3. Connect the two

In Render, open **stepcheck-api → Environment** and set:

| Variable | Value |
|---|---|
| `CORS_ORIGINS` | The Vercel production URL, e.g. `https://stepcheck.vercel.app`. Add a custom domain too if you use one, comma-separated. |
| `CORS_ORIGIN_REGEX` | Optional. Allows Vercel preview deploys, e.g. `https://stepcheck-[a-z0-9-]+\.vercel\.app`. The whole origin must match. Make the pattern as narrow as your project's URLs allow. |

Saving restarts the service.

## 4. Adding AI later

**Free option (Google Gemini):** the client works with any OpenAI-compatible endpoint, so it can call Gemini's free tier directly. Create a key at https://aistudio.google.com/apikey **in a new project**. A key in an existing Cloud project may have a free quota of 0, and Google then answers every request with 429. Set `OPENROUTER_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai` and `OPENROUTER_API_KEY` to the Gemini key. Set the model IDs, without a `models/` prefix:

- vision: `gemini-3.5-flash`
- text: `gemini-3.5-flash-lite`
- fallback: `gemini-3.1-flash-lite`

These passed the smoke test in November 2026. Gemini 2.5 models are closed to new users. The variable names still say OPENROUTER. Google may use free-tier prompts, including uploaded images, to improve its products.

Otherwise, set `OPENROUTER_API_KEY` and the three `OPENROUTER_*_MODEL` values in Render. Set `OPENROUTER_APP_URL` to the Vercel URL. Before relying on the models, test them locally with `backend/scripts/smoke_openrouter.py`.

## Testing the live site

Open the Vercel URL and check:

- [ ] The landing page loads, and **Check my solution** opens the workspace.
- [ ] *Correct linear solution*: every step is green.
- [ ] *Arithmetic slip*: step 3 is the first error and step 4 is downstream.
- [ ] **Explain mistake** returns text. Its label says *template* until a key is set.
- [ ] *Calculus → Product rule slip*: step 2 is the first error and **Explain mistake** names the product rule.
- [ ] *Calculus → Missing + C*: the result is *Unfinished*.
- [ ] **Visual editor** loads (a short wait the first time) and its steps check like typed ones.
- [ ] **Guide me through it** reaches *Solved*, and **Show corrected solution** shows a re-checked answer.
- [ ] Refresh the results page and the results are still there.
- [ ] **Upload photo**: without a key, this shows a clear "AI unavailable" message. With a key, upload a sample from `examples/handwritten_samples/`.
- [ ] The page works at phone width.
- [ ] The browser console shows no CORS errors.

### Cold starts

Render's free tier stops the service after about 15 minutes without traffic, and the first request after that can take up to a minute. To reduce the wait, every page sends a request to `/api/v1/health` as soon as it loads, so the server starts waking while the student types. If a request still times out, the message says the server may be starting and to try again. **Before a live demo, open the site a minute early,** or use a paid instance that doesn't sleep.

A restart also clears saved verifications. The frontend then re-sends the steps, so students don't lose their work.

### Checking the rate limiter

`TRUSTED_PROXY_HOPS=2` assumes requests reach the app through two proxies, Cloudflare and Render's own proxy, each adding one entry to `X-Forwarded-For`. Render's documentation doesn't spell this out, so confirm it after deploying:

1. **Spoofed headers must not bypass the limit.** Send more `/verify` requests than the limit allows (120 per minute by default; lower `RATE_LIMIT_VERIFY_PER_MINUTE` while testing), each with a different fake header. Once you pass the limit, you should get `429`:
   ```powershell
   '{"steps":["2x = 4","x = 2"]}' | Set-Content -Encoding ascii body.json
   1..130 | % { curl.exe -s -o NUL -w "%{http_code} " -H "X-Forwarded-For: 10.0.0.$_" -H "Content-Type: application/json" --data-binary "@body.json" https://<your-service>.onrender.com/api/v1/verify }
   ```
   The body is read from a file because Windows PowerShell 5.1 breaks inline JSON apart when it passes it to `curl.exe`.
2. **Different users must get separate limits.** While your laptop is rate-limited, a request from your phone on mobile data should still succeed.

What to do if a check fails:

- **Check 1 fails** (spoofed headers get through): the setting is too high and is reading an entry the client wrote. Lower it by one.
- **Check 2 fails** (every user shares one limit): the setting is too low and is reading a proxy's address. Raise it by one.
